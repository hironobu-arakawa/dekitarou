# デキタロウ — 受注者向けMVP 仕様書 (specs.md)

このファイルは Claude Code に渡して実装させるための仕様書である。
実装者はこの仕様の範囲を勝手に広げないこと。迷った場合は「作らない」を選ぶ。

---

## 0. 一行で言うと

**現場（OT）で小さなDX案件を受注しようとするエンジニアが、現場に入る前に読むサイト。**

売っているのは技術解説ではなく、「その案件を仕事として閉じるための作法」である。

---

## 1. なぜ受注者向けなのか（実装判断の前提）

発注者向け（工場に売る）の市場はすでに埋まっている。

- 現場帳票のデジタル化は完成品SaaSの領域（i-Reporter、Platio、kintone、カミナシ等）
- 小規模IoT受託も既存業者が同価格帯で営業済み（温湿度監視で初期30〜80万円が相場）
- 現場DX解説メディアも飽和。ほぼ全て自社ツールへの導線

一方で空いているのは、**OT現場特有の受注作法**である。世に出回っているヒアリングシート・見積テンプレートはIT一般／営業一般向けで、次を扱っていない。

- 活線作業の可否、設備を止められるのか
- 電気工事士等の資格がどこから必要になるか
- 設備に影響を与えた場合の責任は誰が持つのか
- 止まった時に誰が復旧するのか
- 動いたPoCを、誰が運用し続けるのか

**このサイトの資産はここ一点に集中させる。** 実装中に「技術解説を厚くしたい」誘惑が出たら却下すること。技術解説はQiita/Zennに無数にあり、差別化にならない。

## 2. ターゲット読者（ペルソナ）

1. **越境してきたITエンジニア** — Web/Pythonはできる。工場案件の話が来たが、現地で何を見ればいいか分からない。
2. **越境しようとしている制御・電気技術者** — 現場は分かる。IT側の見積の立て方と保守条件の切り方が分からない。
3. **社内の現場改善担当** — 外注する側だが、自分で作る判断もする。受注者の作法を知りたい。

主読者は1。文章は「1に向けて、現場を知っている人間が書く」トーンで統一する。

## 4. MVPの中身

### 4.1 コンテンツの2階層

**(A) 案件カード — 10件**

案件単位の実務ドキュメント。これがサイトの核。1件あたり2,000〜4,000字程度。

**(B) 横断ドキュメント — 3本**

案件をまたいで共通する作法。サイトの思想が最も出る部分。

1. `現場に入る前チェックリスト` — 初回訪問で確認すべきこと
2. `責任分界の決め方` — どこまでが自分の責任か、契約前に決める手順
3. `資格・法令の早見表` — 電気工事士、電気主任技術者、無線、消防、機械安全がどこから関わるか

### 4.2 初期案件カード10件（この10件で作る）

受注しやすさ順ではなく、**責任分界の説明力が高い順**に選んである。

| # | slug | タイトル | 責任分界の論点 |
|---|------|---------|--------------|
| 1 | `temp-humidity-monitor` | 温湿度を遠隔監視する | 設備に触れない案件の基準形。ここが最も安全な入口 |
| 2 | `current-clamp-logging` | 設備の電流値を記録する | クランプ式なら非接触。だが取付は誰がやるのか |
| 3 | `plc-data-export` | PLCデータをCSVで吸い出す | 読み取り専用の徹底。書き込みは絶対に請けない |
| 4 | `operation-time-visualization` | 設備の稼働時間を見える化する | 「稼働」の定義を誰が決めるか。数字が独り歩きするリスク |
| 5 | `alert-notification` | 異常時にメール／チャット通知する | 通知が届かなかった時の責任。安全装置との明確な分離 |
| 6 | `webcam-monitoring` | Webカメラで設備を監視する | 労務・プライバシー。撮影範囲の合意 |
| 7 | `inspection-form-web` | 点検表をWeb化する | 既製SaaSに勝てるか。作らない判断をどう提案するか |
| 8 | `excel-automation` | Excel集計を自動化する | 属人ファイルの引き取り。元ファイルが変わったら誰が直すか |
| 9 | `legacy-equipment-data` | 古い設備からデータを取り出す | 接点出力・アナログ出力の扱い。ここから有資格者領域 |
| 10 | `energy-visualization` | エネルギーデータをグラフ化する | 計量法と、報告用途に使われた場合の数値責任 |

各カードには必ず **「この案件を受けない方がいい条件」** を書く。これがサイトの信頼を作る。

### 4.3 案件カードの必須セクション

すべてのカードが同じ順序・同じ見出しを持つ。読者が比較できることを優先する。

1. `どんな依頼か` — 現場から来る生の言葉（例：「事務所から機械が動いてるか見たいんだよ」）
2. `本当の要件` — 生の言葉を要件に翻訳する。ここで規模を膨らませない
3. `構成の選択肢` — 2〜3案。それぞれ費用と難易度が違うもの
4. `責任分界図` — **後述の専用コンポーネントで表示（サイトの signature）**
5. `現地調査項目` — チェックリスト形式
6. `顧客に聞くこと` — 質問文そのものを載せる。言い換え可能な形で
7. `資格・法令の要否` — 該当なしの場合も「該当なし」と明記する
8. `見積の考え方` — 金額そのものより、何に時間がかかるかの内訳
9. `落とし穴` — 実際に失敗しうる点
10. `受けない方がいい条件` — 撤退基準
11. `納品条件と保守` — どうなったら「完了」なのか

## 5. 責任分界図（signature element）

このサイトが記憶される唯一の要素。ここに実装コストを集中させる。

### 仕様

案件ごとに、システムを **層** に分け、各層の責任者を色帯で示す横型の図。

```
┌─────────────────────────────────────────────┐
│ 設備本体            │ 顧客（触れない）        │
├─────────────────────────────────────────────┤
│ センサー取付        │ 有資格者／顧客手配      │
├─────────────────────────────────────────────┤
│ 収集・変換          │ 受注者 ★              │
├─────────────────────────────────────────────┤
│ 保存・可視化        │ 受注者 ★              │
├─────────────────────────────────────────────┤
│ 判断・処置          │ 顧客（ここは渡さない）   │
└─────────────────────────────────────────────┘
```

### 実装要件

- Astro コンポーネント `ResponsibilityBoundary.astro` として実装
- データは案件カードのfrontmatterから受け取る（後述スキーマ）
- 責任者は4値のみ： `contractor`（受注者） / `customer`（顧客） / `licensed`（有資格者） / `shared`（協議）
- `shared` は視覚的に警告色にする。**協議 = 未決 = 最大のリスク**という思想を色で表現する
- 静的SVGまたはCSS Grid。JSでのアニメーションは不要
- モバイルでは縦積みに崩れること
- 各層に1行の補足テキストを付けられること

## 6. サイト構成

```
/                          トップ
/cases/                    案件カード一覧
/cases/[slug]/             案件カード個別
/guides/                   横断ドキュメント一覧
/guides/[slug]/            横断ドキュメント個別
/about/                    このサイトについて（書き手の立場を明示）
/contact/                  問い合わせ
```

### トップページ

ヒーローは大きな数字やグラデーションにしないこと。

**開幕に置くのは、責任分界図そのもの。** 「動いた」と「使える」の間に何があるかを、1画面で見せる。その下に案件カード一覧。

キャッチは以下を基本線とする（実装時に微調整可）：

> 動いた、では終わらない。
> 止まった時に誰が直すのかまで決めて、はじめて「できた」。

### /about/ に必ず書くこと

- 書き手は現場側の人間であり、特定製品のベンダーではないこと
- 掲載内容は一般論であり、個別案件の可否判断は読者の責任であること
- 具体的な企業名・案件名は一切扱わないこと

## 7. 技術仕様

### スタック

- **Astro 5** — Content Collections でMarkdownを型付き管理
- **CSS** — 素のCSS（またはCSS Modules）。Tailwindは使わない。トークンをCSS変数で定義する
- **ホスティング** — Cloudflare Pages（静的ビルド）
- **フォーム** — 外部フォームサービス（Tally / Formspree）を埋め込む。バックエンドは持たない
- **解析** — Cloudflare Web Analytics（Cookieを使わないもの）
- JavaScriptは最小限。案件カードは完全に静的HTMLで成立すること

### ディレクトリ

```
src/

    cases/          *.md（案件カード10件）
    guides/         *.md（横断ドキュメント3本）
  components/
    ResponsibilityBoundary.astro
    CaseCard.astro
    Checklist.astro
    Callout.astro          （警告・注意用）
  layouts/
    Base.astro
    Case.astro
    Guide.astro
  pages/
  styles/

```

## 8. デザイン方針

読者はエンジニアであり、装飾を信用しない層である。**計装ドキュメント／設計図面の質感**を狙う。

### やらないこと

- クリーム地＋セリフ見出し＋テラコッタ差し色（生成AIの定番配色）
- 角丸カード＋淡いドロップシャドウの並列レイアウト
- 意味のない 01 / 02 / 03 の連番装飾
- ストックフォトの工場写真、抽象的なネットワーク図

### トークン（実装者が確定させ、tokens.css に落とすこと）

- **配色** — 図面・計器盤の語彙から取る。基調は無彩色寄り、責任者4区分に明確に異なる色相を割り当てる。`shared`（協議＝未決）だけが目を引く警告色であること
- **タイポ** — 見出しと本文で異なるファミリー。数値・チェックリスト・型番用に等幅を1書体。日本語Webフォントは読み込み速度を優先し、可変フォント1つに絞る
- **レイアウト** — 案件カードは11セクションが固定順で並ぶ長文ページ。**追従する目次を左に置き、現在位置を示す**こと。現場でスマホから読まれる想定なので、モバイルでは目次を折りたたむ
- **罫線** — 装飾ではなく、責任の境界を示す時だけ使う。境界線に意味を持たせる

### 品質の下限

レスポンシブ、キーボードフォーカス可視、`prefers-reduced-motion` 尊重、Lighthouse 90+。

## 9. 執筆ルール（コンテンツ生成時の制約）

**重要：** 実在の企業・工場・案件を特定できる記述を一切書かないこと。すべて一般化された型として書く。

- 具体的な製品名は、一般名詞で代替できる場合は一般名詞を使う
- 数値（費用・工数）は幅で示し、断定しない
- 法令・資格については「該当する可能性がある」と書き、最終判断は読者と所轄官庁に委ねる
- 安全に関わる記述では、必ず「安全装置の代替にはならない」旨を明記する
- 「〜すべき」より「〜しないと、こうなる」で書く。読者はエンジニアであり、理由なしの命令を嫌う

```
本サイトの内容は一般的な情報提供であり、個別案件の技術的妥当性・法令適合性を保証するものではありません。
電気工事、設備改造、安全装置に関わる作業は、必ず有資格者および設備所有者の判断のもとで実施してください。
本サイトで紹介する仕組みは、いずれも安全装置・保護装置の代替とはなりません。
```

## 11. 実装の進め方

1. Astro プロジェクト初期化、Content Collections とスキーマ定義
2. デザイントークン確定（tokens.css）→ Base レイアウト
3. `ResponsibilityBoundary.astro` を先に作る。**ここが決まらないと他が決まらない**
4. 案件カード1件（`temp-humidity-monitor`）を完成させ、テンプレートとして固定する
5. 残り9件を同じ構造で展開
6. 横断ドキュメント3本
7. トップ・about・contact
8. Cloudflare Pages へデプロイ

**4 の時点で一度止めて、レビューを受けること。** 1件目の型が全体を決めるため、10件書いてから直すのは手戻りが大きい。

## 12. 公開後の観測指標

PVは追わない。見るのは以下のみ。

- 案件カードの読了率（スクロール深度）
- 「責任分界」「受けない方がいい条件」セクションへの到達率
- 問い合わせ数と、その内容が受注者側からか発注者側からか
- どの案件カードが最も読まれたか（＝次に厚くする対象）
